# バージョンの付け方

バージョンは `package.json` の `_v` に書く。Bot に `v` や `バージョン` とメンションすると、この値が返る。

```
2.0.1-mk2.1.0
└─┬─┘ └─┬─┘
  │     └─ このフォークのバージョン(mk<X>.<Y>.<Z>)
  └─ 取り込んでいる upstream(`syuilo/ai`)のバージョン
```

## フォーク側の番号(X.Y.Z)

[semver](https://semver.org/lang/ja/) に合わせる。

| 桁 | 上げるとき |
|---|---|
| X | 破壊的変更 |
| Y | 機能追加 |
| Z | 不具合修正 |

- 1つの変更に複数の種類が混ざるときは、高い桁で上げて、それより下の桁は 0 に戻す(`mk2.1.3` から破壊的変更なら `mk3.0.0`)。
- 上げるのは、機能の変更と同じコミットか、`chore: バージョン表記を…にする` のコミットで行う。push のたびには上げない。
- **push していない変更は、1つのバージョンにまとめる**(本番に出ていない版を、changelog に残さない)。機能ごとのコミットでは上げず、push の直前に、前回 push した版から1回だけ上げる。
  種類が混ざるときは、上の規則のとおり高い桁で上げる(機能追加と不具合修正が混ざれば Y)。
- 見た目や言い回しだけの変更、`docs`・`chore`・`ci`・`refactor`(挙動を変えない整理)・`test`(テストだけの変更)は上げない。
- 目安は、コミットの種別(`feat` なら Y、`fix` なら Z)。
- 上げたら、[changelog.md](changelog.md) に変更内容を追記する(同じコミットで)。

### 破壊的変更とみなすもの

次のどれかに当てはまる変更。

- 保存データ(`data/` のコレクションの構造)を変えて、古いデータがそのままでは使えなくなる。
- `config.json` に必須項目が増えて、デプロイ時に手作業が要る。
- 既存のコマンドや応答の仕様が変わる。

破壊的変更のコミットには、本文に移行の手順を書く。

## upstream を取り込むとき

`git merge upstream/master` で `_v` の行が競合したら、upstream の部分だけを新しい値に書き換える。
フォーク側(`mk` 以降)の番号は変えない。

```diff
-	"_v": "2.0.1-mk2.1.0",
+	"_v": "2.0.2-mk2.1.0",
```

取り込んだ内容で挙動が変わる場合のフォーク側の番号は、取り込みとは別に、上の表に従って判断する。
